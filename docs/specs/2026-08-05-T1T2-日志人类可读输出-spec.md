# T1/T2 日志人类可读输出规范

## 背景

`ssv-runner` 当前把所有事件以单行键值记录写入 `stderr`。这种格式适合机器解析，但
`runtime_resolved` 和 `inference_stats` 的字段较多，终端阅读时不易区分解码、显示、推理
和延迟统计。

## 目标

1. 终端 stderr 使用分组、缩进和固定字段宽度展示运行时与推理统计。
2. stderr 被重定向到文件或管道时继续输出原有单行结构化键值记录。
3. 不改变事件名称、字段名称、字段值语义、转义规则、截断规则和 fatal 兜底。

## 输出契约

`SsvEventLogOptions::format` 提供两个值：

- `Structured`：单行 `key=value`，为默认值，也是机器消费格式。
- `Pretty`：面向终端的多行格式；首行保留 `event`、`source_id` 和
  `run_attempt_id`，后续按事件职责分组。

runner 创建 stderr logger 时通过 `isatty(STDERR_FILENO)` 选择格式。终端使用 `Pretty`，
非终端使用 `Structured`。日志 sink 接口不感知格式，未来异步 sink 仍接收完整编码记录。

`runtime_resolved` 至少按 `decode`、`display`、`inference` 和 `model` 分组；
`inference_stats` 至少按 `throughput` 和 `latency_ms` 分组，并将每个阶段的 p50/p95
对齐显示。其他事件也使用相同的首行上下文和分组风格，但不新增字段。

结构化记录仍先执行 `max_record_bytes` 限制和现有截断逻辑。pretty 记录只用于人类展示；
当展示结果超出限制时回退到已截断的结构化记录，保证日志边界可控。

## 非本阶段范围

- 不新增日志级别、颜色、时间戳或环境变量配置。
- 不改变异步 sink、fatal flush、stderr 兜底写入和事件 schema。
- 不把多行 pretty 输出用于 Redis、事件 JSON 或其他机器协议。

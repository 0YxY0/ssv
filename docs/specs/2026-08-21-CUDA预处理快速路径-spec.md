# CUDA 预处理快速路径 spec

## 目标

在不改变原始 ONNX 输入契约和现有坐标语义的前提下，为直接 TensorRT runtime
增加可选 CUDA 预处理快速路径。第一阶段继续使用分析分支产生的 model-sized
RGBA canvas，但不再由 CPU 完成颜色选择、归一化和 NCHW 写入；同一 TensorRT
CUDA stream 上把 RGBA 字节复制到 device，再由一个 CUDA kernel 直接写入
TensorRT 的 float32 NCHW 输入 binding。

CPU `SsvImagePreprocessor` 始终保留，并作为 `auto` 模式不可用时的可靠 fallback。
硬件路径的可用性必须由实际 adapter 能力报告，不能根据配置或模型文件名假设。

## 范围

本阶段包含：

- `inference.model.preprocess.execution` 的显式配置：`auto`、`cpu`、`cuda`；
- 原始 RGBA model canvas 到 float32 NCHW 的 CUDA 融合 kernel；
- 直接 TensorRT backend 在同一 execution stream 上复用输入 binding 和 RGBA
  scratch device buffer；
- engine 根据 backend 能力选择 CPU 或 hardware preprocess seam；
- CUDA 预处理时间与 host-to-device、TensorRT execution、device-to-host 分开
  表达；
- 无 CUDA compiler、无 adapter 或测试 fake backend 时仍可构建并走 CPU 路径。

## 非本阶段范围

- ONNX Runtime CUDA/TensorRT EP 的 device tensor 输入；
- NV12、DMA-BUF、VAMemory 或 GPU surface 直接作为预处理输入；
- 在 CUDA kernel 内完成 resize/letterbox；model canvas 的几何仍由 GStreamer
  `videoscale`/`vapostproc` 负责；
- 跨 backend 的零拷贝承诺、异步跨 stream 共享或多路并发输入 buffer；
- 通过模型文件名、metadata 或 engine manifest 推断颜色顺序和归一化；
- 自动切换到另一种 runtime 或修改 TensorRT engine。

## 配置契约

```yaml
inference:
  model:
    preprocess:
      execution: auto # auto | cpu | cuda
```

默认值为 `auto`。语义如下：

| 值 | 行为 |
| --- | --- |
| `cpu` | 始终使用 `SsvImagePreprocessor`，不创建 CUDA 预处理资源。 |
| `auto` | backend 宣布支持且 adapter 已构建时使用硬件路径，否则使用 CPU。 |
| `cuda` | 要求当前 backend 提供 CUDA 预处理能力；不满足时在启动阶段失败。 |

第一阶段只有直接 TensorRT backend 可以宣布支持。ONNX Runtime（包括 CUDA EP）
在本阶段对 `auto` 走 CPU，对 `cuda` 返回明确的启动错误。

配置错误属于 `SsvConfigError`，包括未知值和错误类型。显式 `cuda` 但运行时
没有可用 adapter 属于 `inference.start` 的模型初始化错误；不得在逐帧阶段静默
改变为 CPU，因为这会使性能和计时语义不可预测。

## 硬件预处理 seam

backend 继续拥有推理输入的 device 资源。engine 只传递一个借用的
`SsvHardwarePreprocessInput`：

- `SsvRgbaFrameView`：由 `SsvAnalysisFrame` 持有，直到 backend 的调用返回；
- `SsvPreprocessPlan`：启动时创建的不可变计划，包含 RGB/BGR、scale、mean、std
  和 model canvas 尺寸。

`InferenceBackend::supports_hardware_preprocess(plan)` 是能力查询；
`infer_hardware(host_view, request, stop_token)` 是可选执行 seam。默认实现回到
普通 `infer()`，因此现有 CPU fake 和 ONNX Runtime backend 不需要拥有 GPU 资源。

TensorRT 实现的顺序固定为：

```text
record timing start
  -> host RGBA -> reusable device RGBA scratch (same CUDA stream)
  -> CUDA RGBA-to-float-NCHW kernel
  -> mark TensorRT execution start
  -> enqueueV3/enqueueV2
  -> device output -> reusable host output
  -> stream synchronize
```

RGBA alpha 通道被丢弃；kernel 不改变 `PreprocessTransform`。输入尺寸、stride、
输出元素数和 dtype/layout 必须在启动时已经由 raw model contract 校验。

## 资源所有权与生命周期

| 资源 | 创建/持有方 | 使用方 | 释放时机 |
| --- | --- | --- | --- |
| CUDA stream | `SsvTensorRtExecutionResources` | TensorRT backend 与 kernel | backend stop/destructor |
| TensorRT device input/output bindings | `SsvTensorRtExecutionResources` | TensorRT execution context | resources reset |
| RGBA device scratch | `SsvTensorRtExecutionResources` | CUDA preprocessor | resources reset |
| host RGBA frame | `SsvAnalysisFramePool` | engine/backend 借用 | 最后一个 frame 引用释放 |
| host float fallback buffer | `InferenceEngine` allocator | CPU preprocessor/backend warmup | engine stop |

硬件路径不得保存 `SsvRgbaFrameView`、GStreamer buffer 或 plan 指针到本次
`infer_hardware()` 返回之后。当前 scheduler 只有一个 in-flight task，因此复用
device input/scratch 不会与另一个推理并发；未来提高并发度必须改为每个 task
独占资源。

## 错误语义

- 启动时模型输入不是静态 float32 `[1,3,H,W]` NCHW，仍由 model contract 拒绝；
- `execution: cuda` 但 backend/adapter 不支持，启动失败并指出 `inference.start`；
- RGBA stride、bytes 覆盖范围、plan 与 binding 不一致，当前 task 失败，不构造
  错误尺寸 tensor；
- CUDA copy、kernel launch、TensorRT enqueue 或 synchronize 失败，当前 task 失败，
  不报告伪造的成功结果；
- `execution: auto` 只在启动能力查询失败时走 CPU，不在一次硬件调用异常后
  无条件重试 CPU；这样避免复用可能已处于未知状态的 CUDA stream。

## 计时契约

硬件路径的 `SsvBackendRunTimings`：

- `h2d_us`：RGBA host 到 device scratch 的 copy；
- `preprocess_us`：CUDA kernel 的颜色选择、归一化和布局写入；
- `execution_us`：TensorRT enqueue 的执行区间；
- `d2h_us`：输出 device 到 host 的 copy；
- CUDA event 不可用或任一 event 失败时，阶段保持 `unmeasured`，整段耗时进入
  `unattributed_us`，不把未知阶段写成零。

engine 对外仍将 `preprocess_us` 映射到 `normalize_layout` 阶段；`color_resize`
仍表示 GStreamer 分支，当前未由 inference engine 伪造数值。

## 一致性与验证

CPU 与 CUDA kernel 必须使用同一 `SsvPreprocessPlan`。至少验证：

1. RGB/BGR、scale/mean/std 的逐元素结果与 CPU reference 一致；
2. alpha 被忽略，stride 大于紧凑行宽时结果不变；
3. TensorRT resources 只创建一次 stream、binding 和 scratch，并在 reset 时按
   逆序释放；
4. `auto` 在 adapter 不可用时仍走 CPU，显式 `cuda` 启动失败；
5. 本地无 GPU 时通过 C++ fake CUDA API、engine seam 和 CPU 测试验证；真实 GPU
   kernel 数值、CUDA event 数据和 TensorRT engine 仍单独标记为未验证。

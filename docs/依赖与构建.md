# 依赖与构建

本文说明本机如何准备 SSV 的系统依赖、Python 环境和 GPU runtime。`./ssv build` 负责探测、准备和验证依赖，并把成功结果写入 `build/ssv-deps.env`；它不会安装系统包、GPU 驱动、Docker、Redis 或 RTSP 服务。

## 依赖分层

| 层级 | 依赖 | 用途 |
| --- | --- | --- |
| C++ 构建 | C++17 编译器、Meson >= 1.1、Ninja、`pkg-config`、CMake、make 或 Ninja | 编译 runner、插件和 managed SDK |
| 视频与显示 | GStreamer >= 1.20、base/video/good/bad/tools、GTK 3 | 解码、pipeline、GTK 显示 |
| C++ 库 | `yaml-cpp` >= 0.7、`hiredis` >= 0.14、`nlohmann-json` >= 3 | 配置、Redis 发布和 JSON |
| 推理与跟踪 | ONNX Runtime >= 1.20、OpenCV >= 4.5、BLAS/LAPACK | 推理、BoT-SORT GMC 和数学运行库 |
| CLI | Python >= 3.12、`uv`、PyYAML、redis | `./ssv`、模型工具和 Redis 运维 |
| Python Agent | Python >= 3.12、`uv`、DeerFlow harness、Qdrant client | 事件消费、复核和索引 |
| 可选基础设施 | Docker Engine >= 24、Compose plugin | 本地 Redis |

根项目和 `agent/` 当前都要求 Python 3.12 或更高版本；两者是独立的 uv 项目，需要分别同步环境。

## Debian/Ubuntu

```bash
sudo apt-get update
sudo apt-get install -y \
  build-essential pkg-config cmake ninja-build meson curl ca-certificates \
  libgstreamer1.0-dev libgstreamer-plugins-base1.0-dev \
  libgtk-3-dev gstreamer1.0-tools gstreamer1.0-libav \
  gstreamer1.0-plugins-base gstreamer1.0-plugins-good gstreamer1.0-plugins-bad \
  libyaml-cpp-dev libhiredis-dev nlohmann-json3-dev \
  libblas-dev liblapack-dev \
  python3
```

Debian/Ubuntu 的系统仓库未必提供合适版本的 `uv`，可使用官方安装脚本后重新打开 shell：

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
uv --version
```

`apt` 本身可行，但 `apt install docker.io` 安装的是发行版维护的 Docker 包，不一定满足本项目要求的版本和 Compose plugin 组合。建议按照 Docker 官方仓库说明配置源，再安装 Docker Engine：

- [Ubuntu 安装 Docker Engine](https://docs.docker.com/engine/install/ubuntu/)
- [Debian 安装 Docker Engine](https://docs.docker.com/engine/install/debian/)

完成官方仓库配置后，安装包为：

```bash
sudo apt-get install -y \
  docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

安装后确认项目实际使用的两个命令都可用：

```bash
docker --version
docker compose version
```

系统仓库没有满足版本或 Provider 要求的 ONNX Runtime C++ SDK 时，CPU/NVIDIA/Intel profile 会按下文使用 managed provider；AMD profile 需要提前准备带 MIGraphX 的 system 或 local SDK。

## Arch Linux

```bash
sudo pacman -S gstreamer gst-plugins-base gst-plugins-good gst-plugins-bad gst-libav gtk3 \
  gst-plugin-gtk yaml-cpp hiredis nlohmann-json cblas blas lapack meson python uv \
  docker docker-compose curl ca-certificates
```

按硬件能力补充：

```bash
# Intel VA 解码和诊断
sudo pacman -S intel-media-driver libva libva-utils

# Intel OpenVINO GPU runtime，可选；不安装时 OpenVINO 可能回退 CPU
sudo pacman -S intel-compute-runtime
```

具体硬件能力仍以 `gst-inspect-1.0`、`nvidia-smi`、系统动态库和 `./ssv build` 的探针结果为准。不要把某个发行版的包名当作所有机器的通用结论。

## Python 环境

根项目使用 `uv sync` 创建或同步 `.venv`，不需要手动创建或激活虚拟环境。完整开发和模型契约测试环境：

```bash
uv sync --extra dev --extra model
./ssv --help
```

需要 `./ssv model export` 时安装导出依赖：

```bash
uv sync --extra dev --extra model-export
```

Agent 环境：

```bash
git submodule update --init --recursive
cd agent
uv sync --extra dev
python -m ssv_agent
```

`./ssv agent` 在 `agent/.venv` 不存在时会自动执行 `uv sync`；手动运行 Agent 或测试前建议显式执行上面的命令。`bge_m3` 是额外依赖，只有启用离线 BGE-M3 embedding 时才需要：

```bash
cd agent
uv sync --extra dev --extra bge-m3
```

如果只做 C++ 构建，不运行模型契约测试，可以不安装根项目的 `model` extra；`./ssv test` 会导入 `numpy`、`onnx` 和 `onnxruntime`，因此运行完整编排测试时必须安装它们。

## Runtime profile

```bash
./ssv build --profile PROFILE
```

| Profile | ONNX Runtime | 默认 Provider | 额外要求 |
| --- | --- | --- | --- |
| `cpu` | managed `1.25.1` | CPU | 不需要 GPU |
| `nvidia` | managed `1.25.1-gpu` | TensorRT -> CUDA -> CPU | CUDA 13；managed TensorRT `10.16.1`、cuDNN 9.25 |
| `intel` | managed 源码构建 `1.25.1` | OpenVINO -> CPU | CMake、编译器、make/Ninja；OpenVINO `2025.4.1` |
| `amd` | system 或 local | MIGraphX -> CPU | 带 MIGraphX Provider 的 `onnxruntime.pc` |
| `auto` | 按检测结果选择 | 对应 profile | NVIDIA -> Intel -> AMD -> CPU |

`--profile` 只决定 ONNX Runtime 推理 profile，不决定视频解码。解码模式由 YAML 的 `sources[0].decode.mode` 决定。`auto` 只检测并选择 profile，发现 GPU 但依赖不完整时会失败，不会静默降级为 CPU。

首次 managed 构建会下载或编译较大的 SDK。默认工作区如下：

```text
.deps/onnxruntime/              CPU/NVIDIA managed artifact
.deps/onnxruntime-openvino/     Intel 源码构建和 OpenVINO
.deps/opencv/{source,build,install}
.deps/tensorrt/                 NVIDIA managed SDK
.deps/downloads/                下载缓存
build/ssv-deps.env              依赖快照
```

`run` 和 `inspect` 只接受成功构建产生的依赖快照，并据此设置 `GST_PLUGIN_PATH` 和运行库路径。切换 profile 或 provider 时重新执行 `./ssv build`；`./ssv clean` 只清理可识别的 Meson 构建目录。

## Provider 配置

默认配置适合新机器。只有明确复用本机 SDK 或调整构建资源时才设置这些变量；变量名和值会在 `./ssv build` 前严格校验。项目根目录的 `.env` 会被统一 CLI 读取，已经存在于进程环境的变量优先于 `.env`；该文件已被 Git 忽略。

| 变量 | 取值或作用 |
| --- | --- |
| `SSV_ONNXRUNTIME_SOURCE` | `managed`、`local`、`system`；AMD 默认 `system`，其他 profile 默认 `managed` |
| `SSV_ONNXRUNTIME_ROOT` | managed 工作区或 local SDK 根目录 |
| `SSV_ONNXRUNTIME_BUILD_JOBS` | Intel managed 源码构建并行度 |
| `SSV_OPENCV_SOURCE` | `managed`、`local`、`system`，默认 `managed` |
| `SSV_OPENCV_MODE` | `enabled` 或 `disabled`；关闭后跳过 GMC 的 OpenCV |
| `SSV_OPENCV_ROOT` | managed/local 工作根目录，默认 `.deps/opencv` |
| `SSV_OPENCV_INCLUDE_DIR` / `SSV_OPENCV_LIB_DIR` | `local` OpenCV 的头文件和库目录，实际版本必须为 `4.10.0` |
| `SSV_OPENCV_BUILD_JOBS` | managed OpenCV 源码构建并行度 |
| `SSV_TENSORRT_SOURCE` | `managed` 或 `system` |
| `SSV_TENSORRT_MODE` | `auto`、`enabled`、`disabled`；NVIDIA 必须为 `enabled` |
| `SSV_TENSORRT_ROOT` | managed TensorRT SDK 根目录 |
| `SSV_TENSORRT_ARCHIVE` / `SSV_TENSORRT_URL` | 本地归档或可直接下载的 TensorRT 归档，二选一 |
| `CUDA_HOME` | managed TensorRT 查找 CUDA Toolkit 的补充路径 |
| `SSV_EXTRA_PKG_CONFIG_PATH` | 额外 `pkg-config` 搜索路径 |
| `SSV_BUILD_DIR` | 构建目录，默认 `build` |

`SSV_ONNXRUNTIME_VERSION` 不再是可配置项；runtime 版本由 `--profile` 固定派生，尝试设置它会被拒绝。这样可以避免同一个构建目录混入不同 ABI 的 SDK。

典型配置：

```bash
# 使用本地 OpenCV 4.10.0 SDK
SSV_OPENCV_SOURCE=local \
SSV_OPENCV_INCLUDE_DIR=/opt/opencv/include/opencv4 \
SSV_OPENCV_LIB_DIR=/opt/opencv/lib \
./ssv build --profile cpu

# NVIDIA 复用系统 TensorRT，但仍必须通过 CUDA/Provider 探针
SSV_TENSORRT_SOURCE=system ./ssv build --profile nvidia

# AMD 使用只读 local ONNX Runtime artifact
SSV_ONNXRUNTIME_SOURCE=local \
SSV_ONNXRUNTIME_ROOT=/opt/onnxruntime-migraphx \
./ssv build --profile amd
```

local ONNX Runtime 根目录需要 `VERSION_NUMBER`、`include/` 和 `lib/`，并提供当前 profile 所需的 Provider 动态库。system provider 通过 `pkg-config` 发现；项目拒绝把不符合 profile 的 SDK 或项目内路径伪装成 system 依赖。

## 依赖检查与排错

```bash
pkg-config --modversion gstreamer-1.0
gst-inspect-1.0 gtksink
gst-inspect-1.0 gtkglsink
./ssv build --profile cpu
./ssv inspect
```

- 构建阶段失败：先看依赖摘要中的 `profile`、`source`、版本和 Provider，再检查对应 SDK 的头文件、`pkg-config` 和动态库闭包。
- `./ssv run` 提示缺少 `ssv-deps.env`：先成功执行 `./ssv build`。
- NVIDIA 构建失败：确认驱动、CUDA 13、`libcudart.so.13`、TensorRT/cuDNN SONAME 和 Provider 动态库属于同一运行时组合。
- Intel 构建耗时较长：这是 ORT/OpenVINO 源码构建，可用 `SSV_ONNXRUNTIME_BUILD_JOBS` 限制并行度。
- GTK 显示不可用：先用 `./ssv inspect` 和 `gst-inspect-1.0` 区分插件注册问题、显示 backend 问题和 RTSP/解码问题。

## 构建后验证

```bash
./ssv inspect
./ssv test

# 已完成构建后，只跑 C++ 测试
meson test -C build --print-errorlogs

# 只跑根项目 CLI/模型契约测试
python -m unittest discover -s scripts/ssv_cli/tests -p 'test_*.py'
```

`./ssv test` 会重新按 `auto` profile 编排构建；如果本机刻意使用了其他 profile，应按需运行上面的单项命令。存在本地 `config/ssv.yaml` 时，它还会尝试 30 秒无头 runner smoke；RTSP、模型、GPU 或显示资源缺失时，环境相关 smoke 可能只记录 warning。

# 检测前端配置

## 边界

当前仓库没有独立的一方 Web 前端。本文中的“检测前端”指 `runner/` 提供的实时检测入口、本地图像显示和检测框 overlay；它负责从 RTSP 输入构建 GStreamer pipeline，不负责网页播放、浏览器控制台或远程 API。

## 配置文件

复制模板后只编辑本地副本：

```bash
cp config/ssv.example.yaml config/ssv.yaml
```

runner 的搜索顺序为：

1. `./ssv run --config PATH`。
2. `SSV_CONFIG_PATH` 指向的文件。
3. 项目根目录 `ssv.yaml`。
4. `config/ssv.yaml`。
5. `/etc/ssv/ssv.yaml`。

`config/ssv.example.yaml` 只用于复制，不会被自动加载。YAML 版本固定为 `2.0`，C++ runner 对未知字段和错误类型严格失败；配置路径、临时 Redis 覆盖和调试日志可用环境变量，运行参数本身应写进 YAML。

## 输入与解码

当前阶段只配置一个 H.264 8-bit RTSP source：

```yaml
sources:
  - id: "camera-01"
    uri: "rtsp://localhost:8554/test"
    codec: "h264"
    protocols: "tcp"
    latency_ms: 200
    decode:
      mode: "auto"
      device: "auto"
```

| 字段 | 说明 |
| --- | --- |
| `sources[0].id` | source 标识，进入日志和发布消息 |
| `sources[0].uri` | 可访问的 RTSP 地址；仓库不会启动 MediaMTX |
| `sources[0].codec` | 当前要求 `h264` |
| `sources[0].protocols` | RTSP transport，常用 `tcp` |
| `sources[0].latency_ms` | GStreamer 接收延迟 |
| `sources[0].decode.mode` | `auto`、`vaapi`、`nvdec`、`software` |
| `sources[0].decode.device` | `auto`、`drm:/dev/dri/renderD<N>` 或 `cuda:<N>` |

`auto` 会按实际元素选择 VAAPI、NVDEC 或 software；显式硬件模式不可用时直接失败，不会静默切换。解码 profile 和 ONNX Runtime profile 是两个独立选择。

## 显示与 overlay

```yaml
display:
  enabled: true
  backend: "auto"
  fps: 30
  gl_backend: "auto"
  overlay:
    enabled: true
    font:
      face: "regular"
      size: 12
    motion_prediction:
      enabled: true
      max_horizon_ms: 300
```

| 字段 | 取值或作用 |
| --- | --- |
| `display.enabled` | 是否创建 GTK 显示窗口 |
| `display.backend` | `auto`、`gtkglsink`、`gtksink` |
| `display.fps` | 显示分支的 drop-only 上限 |
| `display.gl_backend` | `auto`、`x11`、`wayland` |
| `display.overlay.enabled` | 是否在独立 GTK 框层绘制检测框 |
| `display.overlay.font.*` | 框层文字样式 |
| `display.overlay.motion_prediction.*` | 仅影响显示时的短时位置预测 |

`gtkglsink` 是严格的 GL/DMABuf 路径；`gtksink` 是显式的 SystemMemory 兼容路径。overlay 不回写视频像素，也不修改 tracker、Redis 事件或证据。

命令行覆盖只存在于本次进程：

```bash
./ssv run --headless
./ssv run --display
./ssv run --display --overlay
./ssv run --display --display-backend gtkglsink
./ssv run --display --display-backend gtksink
```

`--display` 与 `--headless` 互斥；`--display-backend` 只接受 `gtkglsink` 或 `gtksink`。没有桌面会话时使用 `--headless`，不要把 GTK 问题误判为模型或 Redis 问题。

## 推理配置

正式推理路径直接读取原始 ONNX。模型必须有唯一的静态 `float32 [1,3,H,W]`、NCHW 输入，输出必须为静态 float32 tensor：

```yaml
inference:
  enabled: true
  analysis_fps: 15
  model:
    path: "models/yolov8n.onnx"
    family: "yolo"
    output_format: "yolov8"
    label_map: "config/model-labels/coco80.txt"
    preprocess:
      color_order: "rgb"
      resize: "letterbox"
      execution: "auto"
      normalization:
        scale: 0.00392156862745098
        mean: [0.0, 0.0, 0.0]
        std: [1.0, 1.0, 1.0]
  runtime:
    type: "onnxruntime"
    providers:
      mode: "auto"
    device_id: 0
    precision: "auto"
    cpu_threads: "auto"
    cache:
      enabled: true
      directory: ""
  confidence_threshold: 0.5
  target_class: "person"
```

- `analysis_fps` 是推理/跟踪/发布分支的抽帧上限；`0` 表示不限流，但仍不积压旧帧。
- `runtime.type` 为 `onnxruntime` 时使用 `.onnx`；TensorRT 实验路径使用 `.engine` 和配套 `manifest`。
- `providers.mode: auto` 使用构建 profile 的 Provider 链；固定顺序时使用 `explicit` 并填写 `order`，例如 `tensorrt`、`cuda`、`openvino`、`migraphx`、`cpu`。
- `target_class` 为空字符串表示不过滤类别；名称必须存在于 `label_map`。
- `preprocess.color_order` 为 `rgb` 或 `bgr`；`resize` 为 `letterbox` 或 `stretch`。
- `preprocess.normalization` 按 `(pixel * scale - mean) / std` 计算；旧的 `/255` RGB 语义对应上面的默认值。
- `preprocess.execution` 为 `cpu`、`cuda` 或 `auto`。ONNX Runtime 当前使用 CPU 预处理，直接 TensorRT 才可能使用 CUDA 预处理。
- 运行时不要求 `ssv.wrapper.*` metadata，也不会生成中间模型；不会根据文件名或 ONNX metadata 猜测颜色和归一化语义。

`--output-format` 支持 `yolov8` 和 `yolo_nx6`。后者要求原模型输出已经是 `[1,N,6]` 的 `x1,y1,x2,y2,score,class_id`。模型导出和验证的更多说明见 [YOLO 推理链路说明](yolo推理链路说明.md) 和 [安全帽模型验证说明](安全帽模型验证说明.md)。

TensorRT 是独立的实验路径。插件只加载已经构建好的 `.engine`，不会在运行时把 ONNX 转成 engine；engine 应在最终运行机器上从同一个原始 ONNX 构建：

```bash
trtexec \
  --onnx=models/yolov8n.onnx \
  --saveEngine=models/yolov8n.engine \
  --fp16

./ssv model manifest \
  --model models/yolov8n.onnx \
  --engine models/yolov8n.engine \
  --output models/yolov8n.engine.json \
  --precision fp16 \
  --tensorrt-version 10.16.1.11 \
  --cuda-runtime-version 13020 \
  --compute-capability 8.9
```

manifest 会记录 engine SHA-256、原始 ONNX SHA-256、engine 输入 I/O、精度、TensorRT/CUDA 版本和 compute capability；加载时拒绝 hash、版本、设备或输入契约不一致的产物。manifest 不承载颜色顺序、归一化、resize 或输出格式。对应 YAML 为：

```yaml
inference:
  model:
    path: "models/yolov8n.engine"
    manifest: "models/yolov8n.engine.json"
    family: "yolo"
    output_format: "yolov8"
    label_map: "config/model-labels/coco80.txt"
  runtime:
    type: "tensorrt-engine"
    device_id: 0
```

## 跟踪与发布

```yaml
tracking:
  enabled: true
  track_threshold: 0.5
  track_buffer: 30
  match_threshold: 0.3
  mock_track: false
  publish_cooldown_ms: 30000
  gmc:
    method: "sparse-opt-flow"
    downscale: 2
```

`ssvtrack` 当前使用 BoT-SORT；`track_id: -1` 表示该对象没有稳定跟踪 ID。`publish_cooldown_ms` 是发布侧的同 source/track 冷却，`0` 关闭发布冷却；它不能把不稳定的 tracker ID 变成可靠业务身份。Agent 消费侧还有独立的 `agent.dedup_*` 兜底配置。

## 环境变量

| 变量 | 作用 |
| --- | --- |
| `SSV_CONFIG_PATH` | 指定 YAML 文件 |
| `SSV_RTSP_URL` | 临时覆盖 `sources[0].uri` |
| `REDIS_HOST` / `REDIS_PORT` | 临时覆盖 Redis 连接 |
| `GST_DEBUG` | 临时覆盖 GStreamer 日志级别 |

模型、runtime、display、tracking 和 RTSP latency 不提供同名环境变量覆盖，以免构建、运行和 Agent 读取到不同配置。

## 启动与排错

```bash
./ssv build --profile cpu
./ssv inspect
./ssv run --headless
GST_DEBUG="ssv*:5,*redis*:4" ./ssv run --headless
```

显示问题排查顺序：先检查 `./ssv inspect`，再用 `gst-inspect-1.0 gtksink`/`gtkglsink` 检查元素，最后确认 RTSP 客户端能否独立播放同一地址。循环文件以 `-c copy` 发布时，如果码流参考帧或时间戳损坏，软件和硬件 decoder 都可能花屏；更换 GTK backend 不能修复输入码流。
